# תוכנית לבניית skill: bank-risk-expert

תוכנית זו תוכננה בשיחה נפרדת (עם `skill-creator`) עבור פרויקט עתידי נפרד — סוכן אוטונומי שמנהל סיכונים על בסיס האפליקציה "הבנק שלנו" (`ha-bank-shelanu`). מסמך זה הוא קלט מוכן לבניית ה-skill "מאפס" בצ'אט חדש.

**הקשר:** הפרויקט הקיים (`הבנק שלנו`) הוא דמו לימודי לאתר בנק, עם סכימת Postgres מלאה ב-Supabase (`db/schema.sql`). הסוכן העתידי יתחבר לאותו פרויקט Supabase, יקבל פקודות חופשיות בעברית מדף admin פשוט, ויבצע פעולות אמיתיות (חסימת כרטיס, אישור/דחיית הלוואה) + יפיק דוחות ל-Google Docs.

---

## 1. גישה לנתונים

- הסוכן מתחבר ל-**אותו פרויקט Supabase** של "הבנק שלנו", עם **service_role key** (לא anon) — עוקף RLS, רואה את כל הלקוחות.
- **קריטי לביטחון:** מפתח ה-service_role לעולם לא נחשף לשום frontend/דף לקוח — רק לריצת הסוכן עצמה (שרת/backend נפרד).
- טבלאות ליבה (הסכימה המלאה כבר קיימת ב-`db/schema.sql` של הפרויקט הקיים — לקרוא משם ישירות, לא לשכפל):
  `profiles`, `accounts`, `transactions`, `cards`, `card_transactions`, `holdings`, `loan_applications`, `audit_log`, `branches`.

## 2. הגדרת "לקוח בסיכון"

ציון מצטבר 0–100, כל אינדיקטור = 25 נקודות אם מתקיים:

| אינדיקטור | נוסחה | סף |
|---|---|---|
| ניצול אשראי | `cards.debt / cards.credit_limit` (סכום לכל כרטיסי אשראי) | > 80% |
| יתרה שלילית/גבולית | `accounts.balance` | ≤ 0 |
| יחס חוב-הכנסה | `SUM(cards.debt) / profiles.monthly_salary` | > 50% |
| הלוואה תלויה | `loan_applications.status = 'review'` | קיים |
| מגמת הוצאה | סכום תנועות שליליות ב-30 יום אחרון > `monthly_salary` | חורג |

**דירוג:** 0-24 = רגיל | 25-49 = לעקוב | 50-74 = בסיכון | 75+ = בסיכון גבוה.

*הערה: המשקלים (25 לכל אינדיקטור) הם הצעה שרירותית וסבירה לדמו — ניתן לכייל בהמשך.*

## 3. הגדרת "כרטיס חשוד"

| אינדיקטור | נוסחה |
|---|---|
| תנועה חריגה בגודלה | `amount` חדש > **2 × MAX(amount) ההיסטורי** על אותו `card_id` (לא ממוצע — כדי לא לתפוס שוב תשלום גדול חוזר לגיטימי כמו שכירות; רק קפיצה חדשה מעל כל מה שנראה אי-פעם) |
| קצב גבוה (velocity) | ≥ 4 תנועות תוך שעה על אותו `card_id` |
| קרוב למיצוי מסגרת | תנועה שאחריה `debt` יעלה מעל 95% מ-`credit_limit` |
| קטגוריה חדשה + סכום גבוה | `category` שלא הופיעה 90 יום אחרונים באותו כרטיס, וסכום מעל החציון ההיסטורי |

*הערה מימוש: כלל 1 ו-2 דורשים "מה קרה לפני התנועה הזו" לכל תנועה — מומלץ לחשב בקוד האפליקציה (Python/Node) על תוצאת שאילתה פשוטה, לא בשאילתת SQL יחידה מסובכת. כללים 3-4 פשוטים ב-SQL ישיר.*

## 4. קריטריונים להחלטת הלוואה (`loan_applications`)

משתמש בפונקציה הקיימת בפועל בפרויקט (`src/utils/loan.js` → `getMaxLoanAmount = round(balance × 3, ל-1000 הקרוב)`) כתקרה עליונה:

1. `amount ≤ getMaxLoanAmount(balance)` — אחרת דחייה אוטומטית.
2. ציון סיכון (סעיף 2): 75+ → `rejected`; 50-74 → `review` (**לא** מוחלט אוטונומית — נשאר ל"review", לא approved/rejected); מתחת ל-50 → `approved`.
3. אין כבר `loan_applications` בסטטוס `submitted`/`review` לאותו `user_id` (מונע כפילות).

*הערה: כרגע `loan_applications` לא בשימוש בפועל בשום מקום בקוד הקיים (`src/pages/loan.js` הוא דמו client-side טהור בלי כתיבה ל-DB) — הסוכן העתידי יהיה המשתמש הראשון בטבלה הזו בפועל.*

## 5. פעולות אוטונומיות + רשת ביטחון

**עיקרון:** הסוכן **אוטונומי לגמרי** — לא מחכה לאישור אדם על אף החלטה בודדת. הכתיבה ל-DB היא ישירה ומיידית.

**חובה בכל פעולה:** שורת `audit_log` (`action`, `entity_type`, `entity_id`, `meta` עם הנימוק/האינדיקטורים שהובילו להחלטה) — לפני/יחד עם הביצוע, כדי שכל פעולה אוטונומית תהיה שקופה ובת-מעקב.

דוגמה (חסימת כרטיס):
```sql
update cards set blocked = true, status = 'blocked' where id = :card_id;
insert into audit_log (user_id, action, entity_type, entity_id, meta)
  values (:user_id, 'auto_block_card', 'card', :card_id,
          jsonb_build_object('reason', :reason, 'trigger', :indicator));
```
דומה עבור `loan_applications` (update status + audit_log עם action `loan_approved`/`loan_rejected`).

**רשת ביטחון (blast-radius protection, לא אישור אנושי):**
- **סף: N = 5** ישויות שנפגעות בפעולת כתיבה **אחת** מאותה פקודה בודדת.
- חל **רק** על פעולות כתיבה (`block_card`, `approve_loan`, `deny_loan`) — לא על דוחות/קריאה.
- **בחריגה מהסף: עוצר, לא מבצע.** מחזיר רשימת הישויות + הנימוק לכל אחת, ומבקש פקודה ממוקדת יותר או אישור מפורש. סיבה: פעולה בהיקף גדול מפקודה בודדת סביר שנובעת מפרשנות שגויה, וקשה להחזיר אחורה — עדיף safe-by-default.
- מומלץ לרשום גם אירוע `safety_stop` ל-`audit_log` כשזה קורה, עם הפקודה המקורית ורשימת הישויות שהיו מושפעות — כדי שאפשר יהיה לבדוק בדיעבד כמה פעמים זה קרה (ראו דוח 6 ב-references/report-templates.md).

## 6. דוחות (Google Docs)

- דורש Google Docs API + OAuth — **מומלץ service account** לדמו (לא צריך הרשאת משתמש אינטראקטיבית בכל פעם).
- **7 תבניות דוח מלאות, כולל שאילתות SQL** — ב-`references/report-templates.md` (באותה תיקייה כמו קובץ זה): רווח והפסד, מידע לקוחות, לקוחות בסיכון, פעילות חשודה בכרטיסים, צנרת הלוואות, פעילות הסוכן (audit trail — **הכי חשוב**, כי אין אישור אנושי לכל פעולה בודדת), לקוחות רדומים.
- כלל אחיד לכל דוח: שורת סיום `הופק אוטומטית על ידי bank-risk-expert · <תאריך> · מבוסס על נתוני דמו בלבד`.

## 7. פענוח פקודות חופשיות (מדף admin פשוט)

דוגמאות:
```
קלט: "תחסום את הכרטיס של דני לוי, נראה לי חשוד"
→ מזהה user_id לפי שם (profiles.full_name), שולף כרטיסים פעילים.
  כרטיס אחד → חוסם + audit_log.
  כמה כרטיסים → מציג רשימה ומבקש בירור (או חוסם את הכי חשוד לפי סעיף 3 — להחליט בבנייה).

קלט: "תיצור דוח רווח והפסד"
→ מריץ תבנית דוח 1 מ-references/report-templates.md, כותב ל-Google Docs, מחזיר קישור.

קלט: "תחשב אחוז לקוחות רווחיים מול מפסידים"
→ "לקוח רווחי" = accounts.balance − SUM(credit debt) > 0 (עקבי עם netAvailable
   ב-src/utils/balances.js של הפרויקט הקיים). מחזיר אחוזים כתשובת טקסט (בלי חובה ליצור דוח).
```

## נקודות פתוחות לבנייה בפועל

1. **שפת המימוש** של הסוכן (Python/Node) — קובעת איזו ספריית Google Docs API להשתמש (`google-api-python-client` / `googleapis`).
2. כשכמה כרטיסים תואמים לפקודת חסימה מעורפלת — לחסום את הכי חשוד אוטומטית, או תמיד לבקש בירור? (לא הוכרע סופית).
3. אם רוצים מדד "זמן ממוצע מבקשה להחלטה" בדוח 5 — צריך migration קטן: `alter table loan_applications add column decided_at timestamptz;`, מתעדכן כש-status משתנה מ-`submitted`.
4. משקלי ציון הסיכון (25 לכל אינדיקטור) — ניתן לכייל אחרי שרואים תוצאות על נתוני הדמו בפועל.
